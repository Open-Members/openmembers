# Verify a committed source snapshot

`npm run verify:source` is an offline check of the exact Git commit at `HEAD`. It detects prohibited local-material paths and a limited set of credential signatures in that commit. It requires Node from `.nvmrc` and Git with the `--no-lazy-fetch` option; unsupported Git versions fail rather than weakening the offline check. It does not install dependencies, contact providers, start Docker or operate a database.

Run it after committing your changes:

```sh
npm run verify:source
```

The tracked index and working tree must be clean according to Git. The command checks staged and unstaged changes separately and refuses either state, including an index that differs from both `HEAD` and the working file. Git index flags such as `assume-unchanged` can hide working-file edits from that check; the inspected content remains the committed Git objects, never those working-file bytes. A change to `HEAD` or tracked state reported by Git during the check invalidates the result. Untracked and ignored files are outside the check and are not read.

This is a post-commit check, not a pre-commit hook. A local commit is not publication. After correcting a finding, create another local commit and check that revision. Do not interpret a passing later commit as clearance of earlier commits.

## What is checked

- Paths for private work, local tool state, real environment files, installation configuration, key files and generated output, including material force-added despite `.gitignore`. Recognized internal planning, handoff, and agent-instruction filenames are refused at the root and in subdirectories, with case-insensitive matching. Local Cloudflare deployment configuration is also excluded.
- Regular Git files only. Symlinks and submodules are rejected instead of following their destinations.
- The two distributed environment templates, `.env.example` and `deploy/application.env.example`, are permitted by exact path. Their contents are still checked like other files.
- Known credential signatures, including private-key headers and selected token/JWT formats. These are explicit pattern checks, not a general entropy detector. Rules apply to code, documentation and tests; no whole directory is exempt from content checks.

The content rules currently cover private PEM key headers, GitHub classic/fine-grained token shapes, Stripe secret/restricted keys, Supabase secret keys and JWTs declaring `service_role` or `supabase_admin`. JWT inspection reads the header/payload; it does not authenticate a signature or determine whether a credential is active. ASCII signatures in binary blobs and UTF-16 in both byte orders are checked. Other token formats and encoded/compressed content can be missed.

The implementation and exact rule identifiers are in [verify-source.mjs](../scripts/verify-source.mjs), with fictitious examples generated by [its tests](../tests/tooling/verify-source.test.mjs). The rules are generic; project-specific names, visuals and asset rights require separate review.

The checker bounds its work and rejects snapshots that exceed a limit:

| Limit | Value |
| --- | --- |
| Regular files | 20,000 |
| Size of one blob | 5 MiB |
| Total file content | 50 MiB |

Git tree metadata is additionally bounded at 8 MiB. At most 100 findings are reported; reaching that bound still fails the check. Credential matching is bounded per blob, including repeated matches on the same line. An unreadable or malformed Git result also fails. Files are not silently skipped to produce success. A larger legitimate project requires a reviewed limit change and corresponding tests.

Git overrides inherited from the environment are removed, and external clean/process filters are refused before inspecting tracked changes. The checker does not modify your Git configuration. Partial/promisor clone configuration is refused before resolving objects, and automatic lazy fetching is also disabled by option and environment. Use a regular local clone with the snapshot's objects available; the check does not fetch missing objects. Hooks, external diff/text conversion and filesystem monitors are not used by the check.

## Results and scope

Success identifies the inspected revision. Findings identify the rule and file location without reproducing the matching credential or source line. Git failures use sanitized diagnostics rather than dumping raw command output. Credential-like filenames require the same redaction as file content.

The CI quality job runs this command after Node setup and before dependency installation. Its tests are part of `npm run test:tooling`. Workflow configuration and successful local tests do not establish that a hosted GitHub run has passed.

`verify:artifact` remains a separate check of completed Next.js tracing manifests. It can run inside a Docker build without Git and does not replace the source check. Neither check examines the complete contents of a final container image.

Passing this gate does **not** establish absence of all secrets, personal data, private visuals, encoded/compressed content or license restrictions. It does not inspect other refs, historical commits, reflogs, untracked files or remote repository settings. Public demo credentials remain intentionally fictitious fixtures. The final source package and any image require their own review tied to an exact revision and artifact.

If the checker finds an actual credential, follow [SECURITY.md](../SECURITY.md). Deleting the string in a later commit does not invalidate the credential at its provider or remove it from history. Keep values and private evidence out of public issues and logs. A false positive requires a narrow, reviewed rule correction or a clearly fictitious fixture; do not disable content checks for an entire folder.
